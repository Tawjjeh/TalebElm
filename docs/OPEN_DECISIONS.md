| 32  | Unlock gate and progress flags | Decided (MVP): `UserProgress.CompletedRequiredProblems` is a stored sticky boolean (default false) and its migration belongs to Phase 3. Let `hasExam` = the Module has an Exam and `hasReq` = it has at least one IsRequired problem. `examGate = !hasExam || PassedExam`. `problemGate = !hasReq || CompletedRequiredProblems`. The next Module unlocks only when `(hasExam || hasReq)` and `examGate` and `problemGate` and a next Module exists. A Module with neither exam nor required problems is unlocked only by the Admin manual-unlock rule. `CompletedRequiredProblems` becomes true when every currently IsRequired problem has a completion and is never cleared; adding a required problem later never re-locks anyone. Unlocking is idempotent (create or update the next progress row). The check runs after both events (exam submit, problem verification) inside one UnitOfWork transaction, which commits even when nothing unlocks. `ProgressResponse` also exposes `RequiredProblemsTotal` and `RequiredProblemsCompleted` in addition to the current fields | [05](features/05-student-enrollment-and-progression.md), [07](features/07-module-problems-and-verification.md), [BUSINESS_RULES](business/BUSINESS_RULES.md) |

The matched version is stored on the completion. A completion is never invalidated by later version changes. `ModuleProblem` gets nullable `GitHubTaskId` FK (`Restrict`) with `CHECK (Kind = CodeforcesProblem implies GitHubTaskId is null, Kind = GitHubTask implies GitHubTaskId is not null)`. The algorithm lives in `ITaskVerificationService.VerifyRepositoryAsync(userId, gitHubTaskId, repositoryName, requiredJobName?, cancellationToken)` and returns a result only; callers record the outcome: the module-problem route records `UserProblemCompletion` and runs the unlock check; the milestone route records `UserMilestoneProgress` and the track-completion check. Replace `POST /api/tasks/{id}/verify` with `POST /api/module-problems/{moduleProblemId}/verify` and keep the milestone verify route; keep `GET /api/tasks/{id}` for read. Verification inspects the jobs of the latest workflow run on the verified head commit. Plain tasks require all jobs to succeed; milestones require only their own job. Hardening notes: the workflow must invoke the test project by explicit path, root build files (`global.json`, `Directory.Build.props`, `NuGet.config`, solution file) must not exist in the template or must be included in the integrity set, Git tree responses may be truncated for large repositories, and the integrity set covers the workflow file, the tests tree, and the root build files | [07](features/07-module-problems-and-verification.md), [10](features/10-automated-task-verification.md), [TASK_TEMPLATE_SPEC](TASK_TEMPLATE_SPEC.md) |
